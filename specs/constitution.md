# 项目宪法（constitution.md）

- 项目代号：web-match-game（Web 益智消除小游戏 MVP）
- 文档版本：v1.1.1
- 最近变更：CR-006（2026-11-10，第 5.2 节「可点击区域」拆分为两类表述：DOM 交互元素仍最小 44×44 CSS px，Canvas 棋盘格热区改按 spec REQ-049 分级要求执行；全部门槛数值不变；CR 记录见 specs/001-core-game/spec.md 第 15 章）

## 1. 目的与优先级

本文件规定不可协商的工程红线。优先级顺序为：

1. 本宪法（constitution.md）
2. 已发布的特性规格（`specs/<编号>-<特性>/spec.md`）
3. 架构设计文档
4. 实现代码与测试用例

当低优先级文档与本文件冲突时，以本文件为唯一依据，并在 24 小时内补登 CR。

## 2. 技术栈红线

### 2.1 强制技术栈（不得替换）

| 项 | 规定值 |
|---|---|
| 语言 | TypeScript 5.x，`strict` 模式必须开启 |
| 构建工具 | Vite 6.x |
| 渲染 | Canvas 2D（HTML Canvas 元素 + 2D context） |
| 运行形态 | 纯前端单页应用，构建产物为静态文件，可直接静态托管运行 |
| 目标运行时 | Chrome / Edge / Firefox / Safari 最近 2 个大版本；移动端 iOS Safari 16+ / Android Chrome 108+ |
| 包管理器 | npm，锁文件（package-lock.json）必须提交 |

### 2.2 依赖白名单

运行时依赖（`dependencies`）必须为 0 个第三方包。允许的 `devDependencies` 仅限：

`typescript`、`vite`、`vitest`、`@vitest/coverage-v8`、`@playwright/test`、`@types/node`

任何白名单外的依赖（含 UI 框架、状态库、动画库、音效库、游戏引擎如 Phaser/PixiJS）必须走 CR 并说明体积、许可证与性能影响，未经批准不得引入。

`@vitest/coverage-v8` 仅用于测试期采集覆盖率（依据 CR-005），不得进入运行时产物；`dependencies` 仍必须为 0，第 6 节第 5 条覆盖率门槛（`core/` 行覆盖率 ≥ 80%、分支覆盖率 ≥ 70%）不变。

### 2.3 绝对禁止项

- 禁止任何后端服务、BFF、SSR 服务端、云函数、边缘函数。
- 禁止任何账号体系：登录、注册、第三方 OAuth、用户资料同步。
- 禁止任何支付、内购、广告、埋点 SDK。
- 禁止任何服务端排行榜、跨设备同步、云端存档。
- 禁止运行时发起跨域网络请求；除同源静态资源（自托管）外，不得请求任何第三方域名。
- 禁止使用 `localStorage` 之外的持久化手段（IndexedDB、Cookie、Cache API 均需 CR 批准）。
- 禁止在 UI 层内嵌业务规则（匹配、计分、胜负判定必须位于纯逻辑模块）。

### 2.4 构建产物要求

- `npm run build` 必须成功，输出 `dist/`，其中只包含静态资源（`index.html`、JS、CSS、图片、音频）。
- 产物必须能在任意静态文件服务器（如 `npx serve dist`）下直接运行，不得依赖 Node 运行时或环境变量注入。
- 必须提供 `npm run preview` 用于本地验证生产构建。
- 产物中不得出现 source map 之外的开发调试代码；生产构建必须移除 `console.debug`。

## 3. 代码规范

| 规范项 | 要求 |
|---|---|
| 语言 | TypeScript strict；禁止 `any`（不得已时须 `// eslint-disable-next-line` 式注释说明理由并登记 CR） |
| 模块划分 | `core/`（纯逻辑：棋盘、匹配、计分、关卡判定）、`render/`（Canvas 绘制）、`audio/`（音频）、`ui/`（DOM 界面）、`storage/`（存档与排行榜）、`main.ts`（装配） |
| 纯函数要求 | `core/` 内所有函数必须为纯函数：不读全局状态、不访问 DOM、不访问 `Date.now()`/`Math.random()`（时间与随机数必须由参数注入） |
| 命名 | 文件 `kebab-case.ts`；类型/接口 `PascalCase`；函数与变量 `camelCase`；常量 `UPPER_SNAKE_CASE` |
| 类型 | 所有对外函数必须有显式返回类型；禁止隐式 `any` 与类型断言链 |
| 状态变更 | 对局状态必须为不可变更新（返回新对象），禁止跨模块共享可变引用 |
| 副作用集中 | 副作用（DOM、Canvas、音频、存储）只允许出现在 `render/`、`audio/`、`ui/`、`storage/` |
| 错误处理 | 禁止吞掉异常；存储与资源加载失败必须以显式降级路径处理并在 UI 提示 |
| 注释 | 公共函数必须写 JSDoc（用途、参数、返回值、边界）；数值常量必须注明来源规格 REQ |
| 文件规模 | 单文件不超过 400 行；单函数不超过 60 行（超出需拆分） |
| 提交规范 | 提交信息格式 `type(scope): subject`，type 取值 `feat/fix/refactor/test/docs/chore` |

## 4. 性能基线

测试环境基线：Chrome 桌面版，Windows 11，4 核 CPU / 8GB 内存；移动端基线 iPhone SE（第 3 代）/ 中端 Android（骁龙 6 系）。

| 指标 | 阈值 | 测量方式 |
|---|---|---|
| 渲染帧率 | 目标 60fps；连续 10 秒对局中 p95 帧间隔 ≤ 20ms，且低于 50fps 的帧占比 ≤ 5% | Chrome Performance 面板录制 + 自建帧统计 |
| 单帧主线程预算 | 画布重绘逻辑 ≤ 8ms | `performance.now()` 打点 |
| 首屏必需传输体积 | ≤ 3.0 MB（gzip 后，含 HTML/JS/CSS/首屏图片/字体） | DevTools Network 面板 "Transferred" 合计 |
| 全量资源体积 | ≤ 8.0 MB（gzip 后，含 BGM 与全部音效） | 构建产物统计 |
| 初始 JS bundle | ≤ 200 KB（gzip 后） | `vite build` 体积报告 |
| 首屏最大内容绘制（LCP） | ≤ 2.5s（Fast 3G + 4× CPU 降速） | Chrome DevTools Lighthouse |
| 可交互时间（TTI） | ≤ 3.0s（同一条件） | Lighthouse |
| 内存占用 | ≤ 200 MB（连续游戏 10 分钟后） | Chrome Memory 面板 |
| 动画调度 | 必须使用 `requestAnimationFrame`；禁止用 `setInterval`/`setTimeout` 驱动逐帧动画 | 代码评审 + 静态检查 |

性能预算不得以牺牲视觉可读性为代价；若阈值无法达成，必须登记 CR 并给出实测数据，不得静默放宽。

## 5. 可访问性与输入

### 5.1 输入方式

- 必须支持鼠标（主键单击选中 + 拖拽交换）与触摸（单指点击 + 滑动交换）两种输入。
- 鼠标与触摸必须共用同一套"格子坐标换算"逻辑，缩放后坐标误差 ≤ 1 个格子的 1/4。
- 键盘操作、手柄操作不在 MVP 范围（见 spec 的 Out of Scope）。

### 5.2 可访问性基线（WCAG 2.1 AA 相关子集）

| 要求 | 阈值 |
|---|---|
| 文本对比度 | 正文 ≥ 4.5:1，大号文本（≥18pt 或 14pt 粗体）≥ 3:1 |
| 可点击区域（DOM 交互元素） | 按钮、开关、列表项等全部可交互 DOM 元素最小 44×44 CSS px；该下限适用于全部 DOM 交互元素，不因视口宽度或画布缩放而降低 |
| 可点击区域（Canvas 棋盘格热区） | 不适用上一行的 44×44 下限，改按 `specs/001-core-game/spec.md` 的 REQ-049 分级要求执行：视口宽度 ≥ 600 CSS px 时单格热区 ≥ 40×40 CSS px；视口宽度 < 600 CSS px 时不设最小像素下限，按 960×720 等比缩放后的实际单格尺寸，并以最近邻格吸附保证命中准确性；相邻格热区不得重叠；REQ-049 中引述的「所有可交互元素最小 44×44 CSS px」为 CR-006 之前的 5.2 旧措辞，现行口径以本表两行为准 |
| 非颜色区分 | 每种游戏元素必须同时具备颜色 + 形状差异，禁止仅靠颜色区分 |
| 色盲模式 | 必须提供开关，开启后元素附加高对比纹理/符号 |
| 动效弱化 | 必须尊重 `prefers-reduced-motion`，并提供手动"减弱动效"开关；开启后消除动画 ≤ 100ms 或直接瞬移 |
| 音频可控 | BGM 与音效必须有独立开关与音量滑块，且状态持久化 |
| 状态播报 | 分数、步数、目标进度的变化必须通过 `aria-live="polite"` 区域播报，且同一秒内最多播报 1 次 |
| 焦点可见 | DOM 按钮必须有可见焦点样式（≥ 2px 轮廓，对比度 ≥ 3:1） |

### 5.3 自适应布局

- 画布逻辑分辨率固定 960×720，按容器等比缩放，保持 4:3 比例，多余空间留边（letterbox），不得拉伸变形。
- 必须支持 320px 宽度至 2560px 宽度、窗口任意缩放、移动端横竖屏切换，且不丢失对局状态。
- 渲染分辨率上限：`min(devicePixelRatio, 2)`，防止高 DPR 设备性能塌陷。

## 6. 可测试性要求

1. **纯逻辑与渲染分离**：`core/` 模块必须能在 Node 环境（Vitest）中无 DOM 直接测试。
2. **确定性随机**：所有随机行为必须通过注入的种子伪随机数生成器（PRNG）产生；相同种子 + 相同操作序列必须得到完全相同的棋盘与分数。
3. **状态可序列化**：对局状态必须能 `JSON.stringify` → 解析 → 恢复，且恢复后继续操作结果一致（无函数、无循环引用、无 `Map`/`Set` 直接落盘）。
4. **规格可追溯**：每条 REQ 必须至少对应 1 个测试用例，用例名包含 REQ 编号（如 `REQ-006 无效交换不扣步`）。
5. **覆盖率门槛**：`core/` 目录行覆盖率 ≥ 80%，分支覆盖率 ≥ 70%。
6. **E2E 覆盖**：Playwright 必须覆盖"开始关卡 → 完成一次消除 → 结算 → 重开 → 刷新后进度保留"完整链路。
7. **禁止 mock 业务规则**：测试中不得复制一份规则实现作为"期望值"，期望值必须来自规格中的数值表。

## 7. 完成定义（Definition of Done）

一个特性/一个关卡"完成"必须同时满足：

1. 对应 REQ 全部实现，且每条 REQ 的验收标准均有通过的测试用例（用例名含 REQ 编号）。
2. `npm run build` 与 `npm run test` 均通过，构建产物无 console error / warn。
3. Lighthouse（生产构建、桌面）得分：Performance ≥ 80、Accessibility ≥ 90、Best Practices ≥ 90。
4. 生产构建下无任何跨域请求（DevTools Network 中第三方域名请求数为 0）。
5. 鼠标与触摸各完成一次完整流程（8 关可通、结算、重开、刷新后进度保留）。
6. 存档与排行榜在刷新、关闭浏览器重开后仍保持；损坏存档可自动恢复且不崩溃。
7. 美术与音频资源清单全部落地；任一资源缺失时走占位降级且不阻断游戏。
8. 性能基线全部达标（见第 4 节）。
9. 规格变更已登记 CR，且 REQ 编号未被静默改写。
10. 代码评审通过，且评审人确认第 2.3 节"绝对禁止项"未被违反。

## 8. 规格流程规则

1. **唯一事实源**：`/specs` 为需求唯一事实源，代码注释与口头约定不构成需求。
2. **REQ 编号**：全局唯一、自增、永不复用；删除需求不得回收编号，只能标记为 `DEPRECATED`。
3. **可测性**：每条 REQ 必须给出 Given/When/Then 或明确数值阈值；凡以模糊占位表述代替可测标准（例如用「未定值」「按情况而定」「大致」「差不多」等措辞替代具体数值、明确分支或明确阈值），即视为规格不合格。
4. **数值表**：所有数值（尺寸、步数、分数、倍率、阈值、时长）必须在规格中以表格形式给出具体值，代码中的常量必须与之逐项一致。
5. **变更控制**：已发布规格的任何修改必须新增 CR 条目（CR-001 起），记录变更原因、受影响 REQ、影响的下游任务；禁止静默改写。
6. **歧义处理**：规格存在歧义时输出「澄清问题清单」并阻断下游；不得自行假设后继续。
7. **非目标必写**：每个特性规格必须包含 Out of Scope 章节。
